# Zero-Budget Next Phase Plan

**Prepared:** 2026-10-21
**Constraint:** GH₵0 / $0 of new recurring spend. Every item below uses code we already own, a free tier we already use, or a free service with no card required. The real currency is engineering time.
**Status:** All 13 original product phases are complete, Sentry is installed and verified end-to-end (issue `ZIYARN-1`), and local gates are green (workspace typecheck 10/10, web lint, production build, 68 + 11 tests). This plan covers what to improve next.

---

## 1. Where the product stands

### What is strong

- **The core loop exists and is verified:** sign up → domain → agent → knowledge base → embeddings → RAG chat → tool calling → escalation → owner messenger → widget.
- **The commercial surface is broad:** Paystack subscriptions, products, bookings, campaigns, analytics, usage, workspaces, admin panel, and a documentation site with 19 pages (~10,300 words).
- **Guardrails are already enforced:** zod at service boundaries, owner-scoped mutations, embed-secret public chat, per-visitor chat limits, plan limits in one module, no module-level mutable state.
- **The widget is dependency-free and small:** Shadow DOM, SSE streaming, history restore, variants, and a real-browser E2E script (`apps/web/scripts/widget-e2e.mjs`).

### Gaps worth fixing now

| Gap | Evidence | Consequence |
|---|---|---|

## 2. How these items were chosen

1. **Protect revenue first.** Billing, scheduled sends, and payment completion outrank new features.
2. **Make failures visible.** Errors, uptime, and backups turn silent failures into known ones.
3. **Remove a repeated manual burden.** A cron job or CI workflow costs nothing and runs forever.
4. **Prefer leverage over novelty.** Fixing metadata, exports, or onboarding helps every user; a new AI feature helps a demo.
5. **No new paid dependency.** Free tiers already in use: Neon, Sentry, GitHub Actions, SMTP, Paystack test mode, UptimeRobot, Google Search Console.
6. **Do not invent social proof.** No testimonials, case studies, or customer logos until they are real.

Effort key: **S** ≤ 1 day, **M** 2–4 days, **L** 1–2 weeks.

## 4. P0 — Launch-safe (weeks 1–3)

### P0.1 Wire the scheduler

**Why.** `apps/web/app/api/campaigns/process-scheduled/route.ts` is guarded by `x-cron-secret`, but nothing in the repo calls it. A scheduled campaign is currently a promise the product does not keep. The same scheduler will later run reminders, pruning, and backups.

**How.**
- Add `.github/workflows/cron.yml`:
  - `on.schedule` every 10 minutes (`*/10 * * * *`) plus `workflow_dispatch`.
  - `curl --fail --silent --show-error "$APP_URL/api/campaigns/process-scheduled" -H "x-cron-secret: ${{ secrets.CRON_SECRET }}"`.
  - Store `APP_URL` as a repository variable and `CRON_SECRET` as a secret.
- Test with `workflow_dispatch`: create a campaign due one minute ahead, run the job, confirm it flips from `scheduled` to `sent`.
- Keep the endpoint idempotent: `processDueCampaigns` must not send twice if two runs overlap. Add a conditional update (`status = 'sending'` or a `locked_at` column) if the current query can race.
- Later, replace the single endpoint with `/api/cron/route.ts` dispatching jobs (campaigns, booking reminders, rate-limit pruning). One workflow, one secret.

**Done when.** A scheduled campaign sends without a human hitting the endpoint; a second concurrent run sends no duplicate; failures appear in the Actions log.

**Effort:** M. **Cost:** 0 (GitHub Actions free minutes).

### P0.2 Finish Sentry as an operating tool

**Why.** The SDK works, but `SENTRY_AUTH_TOKEN` is currently empty, so production builds cannot upload source maps. There are no alert rules, and the dashboard error boundary does not report to Sentry. That is telemetry, not operations.

**How.**
- Create an organization auth token in Sentry with `org:ci` and project release scopes. Set `SENTRY_AUTH_TOKEN` in Vercel (all environments) and locally; never commit it.
- Confirm a production build logs a source-map upload and a deliberate test error shows original file/line names.
- Add `Sentry.captureException(error)` in `apps/web/app/dashboard/error.tsx` (use a small client wrapper or `useEffect`, matching `global-error.tsx`).
- Add alert rules for: new issue, regression, 5xx rate spike, errors tagged `route:/api/chat`, and webhook failures (`/api/webhooks/*`, `/api/billing/paystack/webhook`). Route alerts to email first; add Slack later only if free.
- Explicitly set `sendDefaultPii: false` and add a `beforeSend` scrub for emails/phone numbers. This app handles customer conversations.
- Ignore expected control-flow errors (validation 400s, `HttpError`, 429s) so the signal stays clean.
- Set `environment` and `release` from deployment metadata so issues can be tied to a deploy.

**Done when.** A production issue has a readable first-party frame; an alert email arrives for a new issue; the dashboard boundary reports; no PII appears in the event.

**Effort:** S–M. **Cost:** 0 (Sentry free tier).

### P0.3 Health endpoint + uptime monitor

**Why.** Sentry catches exceptions, not a site that is down or a database that is unreachable. There is no health endpoint or monitor today.

**How.**
- Add `apps/web/app/api/health/route.ts`: run `SELECT 1` with a short timeout, return `{ status: "ok", db: "ok", time }` or HTTP 503. No secrets, no auth.
- Add a free UptimeRobot monitor (5-minute HTTP keyword check on `"status":"ok"`) with email alerts.
- Optional: a static `/status` page that explains current known issues. Keep it honest; do not claim an SLA.
- Add the endpoint to the deployment docs.

**Done when.** The monitor is green; stopping the database (or pointing at a bad URL locally) flips the check to 503 and sends an alert.

**Effort:** S. **Cost:** 0.

### P0.4 CI pipeline

**Why.** The repo has no `.github/`. Typecheck, lint, tests, the production build, and the widget browser test only run when someone remembers them. The widget E2E is especially valuable because its failure mode is silent.

**How.**
- Add `.github/workflows/ci.yml` on `pull_request` and `push` to `main`:
  - `pnpm/action-setup` with the pinned pnpm version, `actions/setup-node` with Node 24 and pnpm cache.
  - `pnpm install --frozen-lockfile`.
  - `pnpm check-types`, `pnpm lint`, `pnpm test`.
  - `pnpm --filter web build` with `NODE_OPTIONS=--max-old-space-size=3072`.
  - Cache `.turbo` and the pnpm store; use `concurrency` to cancel superseded runs.
- Add a second job for `pnpm --filter web test:widget` on `ubuntu-latest` (Chrome is preinstalled). If Chrome is not on `PATH`, install it or set `CHROME_PATH`.
- Optional non-blocking job: `pnpm audit --prod --audit-level high` and a weekly Dependabot config.

**Done when.** A deliberately broken type or test fails the PR; `main` is green; the widget job runs on every PR.

**Effort:** S–M. **Cost:** 0 within free minutes (2,000/month for private repos, unlimited for public).

### P0.5 Auth lifecycle

**Why.** `apps/web/lib/auth.ts` enables email/password but has no email verification, no forgot/reset password, and no explicit auth rate limit. A user who forgets a password currently has no self-service route. Admin sign-in has no lockout either.

**How.**
- Add Better Auth hooks using the existing transactional email service (`sendTransactional` in `services/api/src/email/server.ts`):
  - `emailVerification.sendVerificationEmail`.
  - `emailVerification.sendResetPassword` (or the current Better Auth equivalent).
- Add pages: `/forgot-password`, `/reset-password`, `/verify-email`, plus a “Forgot password?” link on `/sign-in`.
- Configure `rateLimit` explicitly for auth endpoints, `trustedOrigins`, and secure cookie settings.
- Decide whether verification is required to use the dashboard. Recommendation: send the email and show an in-app banner, but do not hard-block existing users on day one.
- Add tests for token single-use, expiry, and unknown-email behavior (do not reveal whether an email exists).
- Admin app: add sign-in lockout and an idle session timeout. MFA can follow; passwords are the bigger risk today.

**Done when.** A reset email arrives through SMTP, the token works once and expires, verification works, repeated failed sign-ins are limited, and no endpoint reveals account existence.

**Effort:** M. **Cost:** 0 (existing SMTP).

### P0.6 Shared rate limiting for public chat

**Why.** `SlidingWindowRateLimiter` keeps buckets in a process-local `Map`. On serverless, each instance has its own map, and every deploy resets it. The 10-messages/minute limit is therefore advisory, not enforced.

**How.**
- Add a `rate_limit_windows` table in the existing Neon database:
  - `key text`, `window_start timestamptz`, `count integer`, primary key `(key, window_start)`.
  - Atomic upsert: `INSERT ... ON CONFLICT (key, window_start) DO UPDATE SET count = rate_limit_windows.count + 1 RETURNING count`.
- Key by `chat:{domainId}:{visitorId}` and fall back to `sha256(ip + salt)` when no visitor ID exists. Do not store raw IPs.
- Keep the in-memory limiter as a fast first layer; consult the database second.
- Fail policy: fail open with a Sentry warning if the database check errors, because the per-domain daily cap and plan limits still apply. Document this choice.
- Prune rows older than the window in the cron job.
- Add tests for the 11th request, concurrent increments, and window reset.

**Done when.** Two server instances share one limit; the 11th message in a minute returns 429; old rows are pruned; an outage degrades gracefully.

**Effort:** M. **Cost:** 0 (Neon free tier).

### P0.7 Paystack verification + payment rail decision

**Why.** The pricing page advertises real plans and the upgrade UI uses Paystack, but the subscription path has never been exercised end-to-end with real webhooks. Separately, portal product payments still use Stripe Connect, which has no keys, so visitors see “pay by email”. The sales promise breaks at checkout.

**How.**
- Run the full matrix in Paystack **test mode** (free):
  - Initialize → redirect → verify → webhook → plan applied to the owner’s domains.
  - Upgrade, downgrade, cancel, and the restore/reconcile button.
  - Failed payment leaves the plan alone.
  - Webhook signature rejects a tampered body; replaying the same event is idempotent.
- Add automated tests for signature verification, replay handling, and plan-transition rules. `services/api/src/paystack/server.test.ts` is the starting point.
- Decide the customer-payment rail:
  - **Option A:** configure Stripe Connect (test mode is free; live fees apply). Keep the existing portal code.
  - **Option B:** move product checkout to Paystack subaccounts/splits, so Ghanaian customers pay in GHS and payouts are automated. This is more work but removes the unconfigured Stripe dependency and matches the pricing currency.
- Record the decision and env requirements in `plan/payments.md` and the docs.
- Do not remove Stripe subscription env vars until the dashboard has one subscription path. If Paystack is the only subscription rail, delete the unused Stripe checkout/webhook routes and their docs.

**Done when.** The test-mode matrix is green; a stored plan reflects payment state; replay is rejected; the payment rail is documented; one real live charge is verified only when it is acceptable to pay the fee/refund it.

**Effort:** M–L. **Cost:** 0 in test mode; live transactions carry success-based processor fees.

### P0.8 Backup and restore drill

**Why.** There is one Neon database and no backup script. A bad migration, a cascade delete, or a mistaken query is unrecoverable today.

**How.**
- Add `scripts/backup-db.sh` using `pg_dump --format=custom --no-owner --no-privileges`, compressed, with a timestamped filename.
- Run it weekly from GitHub Actions, upload the dump as a private artifact with 14-day retention. Never attach it to a public release.
- Write `docs/restore.md`: create a Neon branch, `pg_restore` into it, run a row-count check on the core tables, then delete the branch.
- Check the current Neon plan’s point-in-time-restore window and document it. Do not assume a window.
- Do one restore into a branch now, while the data is small.

**Done when.** A dump restores into a Neon branch with matching row counts for users, domains, agents, conversations, messages, leads, and payments; the steps are documented.

**Effort:** S–M. **Cost:** 0 (existing Neon plan, private artifact).

### P0.9 Security headers and CSP

**Why.** `next.config.js` has no `headers()`. The app is missing HSTS, `X-Content-Type-Options`, `Referrer-Policy`, `Permissions-Policy`, and clickjacking protections. The admin app has the same gap.

**How.**
- Add a `headers()` block in `apps/web/next.config.js`:
  - `Strict-Transport-Security` (production only), `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, a minimal `Permissions-Policy`, and `Content-Security-Policy-Report-Only` first.
- Do not break the widget: it is a script embedded on customer sites, not an iframe of our pages. `frame-ancestors` on our app pages is fine; CORS on `/api/chat` is separate.
- Test `/`, `/docs`, `/pricing`, `/dashboard`, `/portal/pay`, and the widget preview with the report-only policy. Fix or explicitly allow the sources Next/Fumadocs need (inline styles/scripts are the usual friction).
- Apply the same headers to `apps/admin/next.config.js`.
- Move to enforcing CSP after a clean report-only window.

**Done when.** Headers are present in production; no CSP violations on the main flows; the widget still loads on a test page.

**Effort:** M. **Cost:** 0.

### P0.10 README + `.env.example`

**Why.** `README.md` still tells people to run `create-turbo`. There is no `.env.example`. A new contributor or operator cannot start without reading the source.

- Add `apps/web/.env.example` with every variable grouped by concern (auth, database, AI, email, Paystack, Sentry, cron), marked required/optional, with no real values. Include `ADMIN_*`, `STRIPE_*`, and `RESEND_*` notes if those paths remain.

- Optional but useful: `docs/runbook.md` with “site is down”, “webhooks failing”, “AI provider 429”, and “restore the database” steps.

**Done when.** A fresh clone can follow the README to a running app; `.env.example` covers every required variable; no secret is committed.

**Effort:** S. **Cost:** 0.

## 5. P1 — Activation and trust (weeks 4–6)

### P1.1 Onboarding to first value

**Why.** The conversational onboarding exists, but the first-run path is the highest-leverage surface: an owner who does not reach a working widget in the first session rarely returns. The current flow also allows “skip to dashboard” before any domain exists.

**How.**
- Walk the flow as a new user and record where it stalls. Verify it creates a domain, a default agent, and (optionally) a starter knowledge document.
- Create a default workspace on first domain creation, so the Team tab is never empty for a solo owner.
- Add a final “Test your agent” step that opens the widget preview with a seeded prompt. This proves value before the dashboard.
- Offer one business-type starter set (FAQ snippets, agent instructions, filter questions) from `services/api/src/domains/business-types.ts`.
- Add lightweight funnel events (server-side inserts, no paid analytics): signup, onboarding start, domain created, agent created, first message, widget copied. These can be simple rows or structured logs.
- Keep the skip path, but send skipped users to a checklist, not an empty dashboard.

**Done when.** A new account can go from signup to a working widget preview in under three minutes; a solo owner has a workspace; the funnel is measurable.

**Effort:** M. **Cost:** 0.

### P1.2 Workspace switcher + domain-scoped navigation

**Why.** Domains are already shared through `workspace_members`, but the dashboard shell lists every accessible domain in one blended view. Conversations call `listConversationsForOwner(userId)` with no domain filter. `plan/domain-tabs-plan.md` lists the remaining tabs and explicitly calls out Conversations as the missing build.

**How.**
- Add a workspace switcher to the dashboard shell (cookie or URL param, server-resolved). Filter `listDomains` by the selected workspace and keep “All workspaces” as an option.
- Add `?domainId=` to `/dashboard/conversations`, pass it through the service, and require a domain selection when the owner has more than one.
- Finish the domain tabs from `plan/domain-tabs-plan.md`: Customers, Orders, Products, Bookings, Analytics are mostly link changes; hide commerce tabs with `getBusinessTypeConfig` flags.

**Done when.** Switching workspaces changes the visible domains; conversations are filtered and labeled by domain; a clinic does not see Products; no owner sees another owner’s data.

**Effort:** L. **Cost:** 0.

### P1.3 Dashboard loading, empty, and error states

**Done when.** A slow query shows a skeleton, a new account sees a guided empty state, a bad URL shows a branded 404, and dashboard errors reach Sentry.

**Effort:** S–M. **Cost:** 0.

### P1.4 Knowledge gaps report

**Why.** The agent already detects a retrieval miss in `services/api/src/chat/tool-executor.ts` (“No knowledge base entry found for this question…”), but the result is discarded. The `tool_calls` table exists and is never written. Owners therefore cannot see what to document next, which is the cheapest way to improve answer quality.

**How.**
- Start writing `tool_calls` rows (name, arguments, result, status) around tool execution. The schema is already in `packages/database/src/schema/index.ts`; use it rather than inventing a second table.
- Add an owner-scoped query that groups `answer_knowledge` misses by normalized query, with domain/agent and last-seen time.
- Surface it on `/dashboard/knowledge` as “Questions your agent could not answer” with a “Create document” shortcut.
- Add a dismiss/resolve action if the list becomes noisy.
- No AI calls and no new infrastructure.

**Done when.** A question with no knowledge match appears in the dashboard within a minute, grouped with a count; resolving it removes it; tool calls are queryable for future analytics.

**Effort:** M. **Cost:** 0.

### P1.5 CSAT (one-tap rating)

**Why.** There is no quality signal after a conversation. Escalation rate and resolution status are proxies, but a one-tap rating is the simplest direct measure.

**How.**
- Migration: `conversations.rating` (smallint 1–5 or `up`/`down`) and optional `rating_comment`, plus `rated_at`.
- Widget: after a conversation is resolved/closed, show a small “How did we do?” prompt that does not block the composer. Respect dismissal.
- API: a visitor-authenticated rating endpoint (conversation visitor token or embed-secret session), one rating per conversation, zod-validated.
- Dashboard: average rating, response count, and recent low ratings on `/dashboard/analytics` or Conversations.
- Alert on a run of low ratings only after there is enough volume; avoid noisy alerts.

**Done when.** A rating persists once per conversation, appears in the dashboard, and cannot be submitted by another visitor.

**Effort:** M. **Cost:** 0.

### P1.6 Export and account lifecycle

**Why.** Owners cannot take their customer data out, and there is no account deletion. That is a trust gap for a product that stores conversations and leads.

**How.**
- Add CSV export for customers/leads (name, email, answers, created date) and orders/payments, owner-scoped, streamed from the service. Reuse the existing table filters.
- Add a JSON export of a workspace (domains, agents, knowledge metadata, conversations, leads) with a size cap and a background job if needed.
- Add “Delete account” in Settings behind typed confirmation and re-authentication. Use Better Auth’s user deletion; verify cascades remove domains, agents, conversations, messages, leads, bookings, payments, and workspace memberships.
- Document retention and what deletion does/does not remove.
- Do not export secrets, embed secrets, or other users’ data.

**Done when.** CSV opens correctly, JSON is complete for the owner’s workspace, deletion removes the account and related rows (verified in a branch), and another user cannot export someone else’s data.

**Effort:** M. **Cost:** 0.

### P1.7 Booking reminders

**Why.** Booking settings and emails exist, but no reminder job does. A reminder 24 hours before an appointment is a cheap reduction in no-shows.

**How.**
- Migration: `bookings.reminder_sent_at` (nullable) and an index on `(starts_at, reminder_sent_at)`.
- Service: `processBookingReminders` selects confirmed bookings starting in the next 24 hours with no reminder, sends the existing transactional email, then stamps `reminder_sent_at`. Use a conditional update to avoid double sends.
- Wire it into the P0.1 cron dispatcher.
- Template: reuse the booking confirmation styling; keep it short and include the signed portal link.
- Respect time zones and the domain’s brand name.

**Done when.** A booking 24 hours out receives exactly one reminder; a cancelled booking receives none; overlapping cron runs do not duplicate.

**Effort:** M. **Cost:** 0 (existing SMTP).

### P1.8 Usage warnings and upgrade path

**Why.** `/dashboard/usage` colors meters red/amber, but it is passive. Owners hit plan limits without warning, which turns an upgrade into a support incident.

**How.**

- Link directly to the billing page and the relevant Paystack checkout.
- Keep the limits in `services/api/src/plans/server.ts`; do not duplicate numbers in the UI.
- Confirm the existing hard gates (chat POST, campaign send) still return clear errors at 100%.

**Done when.** Seeded usage triggers the banner; the 80% email sends once; the 100% behavior is clear and does not silently drop messages.

**Effort:** S–M. **Cost:** 0.

## 6. P2 — Differentiation (weeks 6–10)

### P2.1 Widget core split, redesign, and accessibility

**Why.** `plan/widget-redesign-spec.md` is detailed and unimplemented: one engine, many shells; a card over a dimmed page; message copy buttons; tool cards with results. The current widget works, but the look and the engine/look coupling limit every future variant. It also has no automated accessibility coverage.

**How.**
- Follow the plan’s Option A: a class-name contract between engine and skin. Move behavior (transport, store, session, SSE, tool events) into `@repo/widget-core`; keep rendering in skins.
- Ship the redesign incrementally: composer pill and card animation first, then message/copy/tool cards, then the modal presentation.
- Keep `classic` working; add the paid variant only when the skin contract is stable.
- Accessibility: focus trap in the open panel, `aria-live` for streaming replies, labelled controls, Escape to close, reduced-motion support, visible focus, and 44px touch targets. The widget runs inside third-party pages, so do not assume global styles.
- Resilience: retry on a broken stream, an offline state, a clear error bubble, and a versioned embed URL.
- Extend `apps/web/scripts/widget-e2e.mjs` for these flows and run it in CI (P0.4).
- Test in a page with aggressive CSS (global `* { box-sizing }`, `line-height`, `font-family`) to prove Shadow DOM isolation.

**Done when.** Classic and the new skin share one engine; keyboard-only and screen-reader paths work; the widget E2E covers open, send, stream, tool card, escalate, retry, and copy; the bundle stays small.

**Effort:** L. **Cost:** 0.

### P2.2 AI eval harness

**Why.** The AI path has no deterministic tests. Free Gemini/OpenRouter quotas make live E2E runs unreliable (the roadmap already hit 429s), and prompt/tool regressions are invisible until a customer sees them.

**How.**
- Extract the AI stream and tool executor behind injectable dependencies in `services/api/src/chat/server.ts` (the service already takes `{ db }`; add `streamChat`/`executeTool`).
- Write a fake provider that emits scripted `AiStreamEvent`s: text deltas, tool calls, multiple tools in one turn, malformed arguments, an empty completion, a rate-limit error.
- Fixtures for: filter questions, RAG hit/miss, `capture_email` + `sell_product` in one turn, escalation, booking slot conflict, and a 20-message context window.
- Assert persisted messages/tool calls, SSE framing, and error codes.
- Run offline in CI. Keep a separate opt-in live smoke test with a hard quota, never in the default pipeline.
- Redact real transcripts before using them as fixtures.

**Done when.** The suite runs without network access, catches a deliberately broken tool/prompt, and is required in CI.

**Effort:** M–L. **Cost:** 0 (no provider calls in CI).

### P2.3 Agent personalization

**Why.** `plan/whats-next.md` flags two TODOs in the chat route: identify the visitor and allow a per-agent system prompt. A known name/email makes the agent feel less generic and reduces repeated questions. The per-agent prompt may already work; verify before building.

**How.**
- Accept optional `customerName`, `customerEmail`, and `customerPhone` in the chat config/request; persist them on the conversation/lead.
- Add them to the system prompt as untrusted data, clearly delimited, never as instructions.
- Verify the agent’s `systemPrompt` overrides the default; if it does, document it and drop the TODO.
- Widget: pass known metadata from the host page (if provided) and remember it in session storage.
- Add tests that a malicious name cannot change tool behavior.
- Keep PII out of Sentry and logs.

**Done when.** Known visitor details appear in the prompt and conversation record; the agent prompt override is confirmed; injection tests pass.

**Effort:** S–M. **Cost:** 0.

### P2.4 Payment rail completion / BYOA

**Why.** Two strategic gaps remain: visitors cannot reliably pay for a product (Stripe Connect unconfigured), and AI usage is a platform cost with free-tier quotas. Fixing the first completes the sales story; the second lets owners absorb AI cost with their own keys.

**How.**
- Execute the P0.7 decision. If Paystack subaccounts/splits are chosen, implement initialize → webhook → split/payout → receipt, with the same idempotency and signature tests as subscriptions.
- If Stripe Connect is chosen, configure test keys, verify the PaymentElement and webhook, and document the live-key steps. Do not run both rails for the same checkout.
- BYOA (optional, follow `plan/byoa-plan.md`): encrypted per-domain provider keys, a “Test connection” action, a fallback to platform keys, and clear error states when an owner key is rate-limited. Encrypt at rest with a key from the environment; never log keys.
- Add a small usage ledger per provider so owners can see token/cost estimates. Keep it approximate; do not invent exact billing.

**Done when.** A visitor can pay for a catalog product in test mode end-to-end; the owner sees the payment; a domain can use its own AI key and fall back safely.

**Effort:** L. **Cost:** 0 platform spend; processor fees only on successful live payments, owner keys for BYOA.

### P2.5 Admin roles and audit trail

**Why.** `plan/admin-roles-plan.md` documents the current state: the admin app is read-only in practice, `role` is not enforced, and there is no audit trail. That is acceptable for one operator, risky for a team.

**How.**
- Implement the plan’s permission map, `requirePermission` helper, and role checks on every page/service.
- Add an audit table (actor, action, target, timestamp, metadata) for sensitive reads/writes.
- Add sign-in lockout and session timeout; MFA if the admin surface grows.
- Add security headers to the admin app (P0.9).
- Do this when a second admin exists or before any destructive admin action is added.

**Done when.** A `viewer` cannot mutate, every sensitive action is audited, and a demoted admin loses access on the next request.

**Effort:** L. **Cost:** 0.

## 9. Free-tier guardrails

| Service | Free allowance to respect | Guardrail |
|---|---|---|
| Neon | Storage/compute limits and autosuspend | Keep the rate-limit table small, prune old rows, monitor size, avoid full-table scans |
| Sentry | Monthly error quota | Sample traces (10% prod), ignore expected 4xx, no session replay |
| GitHub Actions | Monthly minutes (private repos) | Cache pnpm/turbo, cancel superseded runs, keep the widget job separate |
| Paystack | Test mode is free; live fees per transaction | Test everything in test mode; verify one live charge only when necessary |
| SMTP | Provider sending limits | Batch campaigns through the existing per-campaign budget; backoff on 429 |
| AI providers | Free-tier quotas | Per-domain daily caps already exist; add caching for embeddings; evals are offline |
| UptimeRobot | Free monitor count/interval | One health check is enough |
| Hosting | **Check the plan terms** | Vercel Hobby is for personal, non-commercial use. Pre-revenue is fine; once charging, either move to Pro (not zero budget) or host on a commercial-friendly free tier (e.g. Cloudflare Workers/OpenNext) or a VPS you already own |

Zero budget does not mean zero risk: free tiers can change. Keep the app portable (env-driven URLs, no proprietary bindings) so a host move is a deployment change, not a rewrite.
